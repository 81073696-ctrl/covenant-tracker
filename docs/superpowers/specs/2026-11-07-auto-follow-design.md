# 卫戍协议记牌器：自动跟随游戏设计

日期：2026-11-07
状态：已实施并通过 197 项 Python 测试及演示服务冒烟；真实游戏识别覆盖率未验证

## 1. 目标与问题

当前插件虽然能识别画面，但识别结果与主要操作仍是两套流程：玩家在游戏里刷新、升级或结束回合后，还要在插件里重复点击对应按钮。这使插件更像手工账本，而不是自动跟随游戏的记牌器。

本次改造以“游戏是唯一操作来源，插件自动跟随”为目标。只读屏幕，不读写游戏内存，不自动点击，不代打。

## 2. 已确认决策

- 高置信度且连续稳定的识别结果直接同步。
- 低置信度或证据不足的变化只提示确认，不写入正式账本。
- 正常自动跟随时，手工动作退到“手动纠错”；识别断开或手工模式下仍保留完整手工操作。
- 分阶段交付：先接通已有识别能力和保守的刷新推断，不承诺首版自动归因所有购买、合成等复杂事件。

## 3. 方案比较

### 3.1 仅隐藏手工按钮

成本低，但没有改变数据流，不是真正的自动化，不采用。

### 3.2 一次性推断全部游戏事件

购买、合成、刷新、升级和过回合同时自动归因，容易把动画、遮挡或误识别写成永久账本记录，首版不采用。

### 3.3 分阶段自动跟随

复用现有视觉管线、观测处理器和状态引擎，增加稳定帧、同步状态、保守事件归因及手动纠错入口。风险可控，采用。

## 4. 范围

### 包含

- 连接可用采集源后自动开始跟随，并允许用户暂停或切换手工模式。
- 将一次抓帧识别作为一个同步批次处理，记录批次状态、最近同步时间与字段置信度。
- 对资金、回合、等级、生命、商店和阵容进行稳定帧校验与高置信度自动同步。
- 在证据充分时自动记录刷新统计；证据不足时提供待确认提示。
- 将对局页主操作区改为跟随状态与异常提示，手工动作收进“手动纠错”。
- 增加后端、前端及回归测试，使用演示帧验证，不修改真实对局存档。

### 不包含

- 自动控制游戏、读写内存或替代玩家操作。
- 首版完整自动归因购买、出售、合成、锁定及所有战斗事件。
- 重写识别模型、概率算法、经济公式或账本格式。
- 承诺任何画面下都能百分之百正确识别。

## 5. 数据流与同步规则

### 5.1 整帧批次

每次抓帧只调用一次视觉管线，将全部观测组成带批次编号的同步结果。每个字段独立判断置信度和稳定性；一个字段不确定不阻塞其他可靠字段，但不得把半帧动画中的不稳定字段写入状态。

后台采集、手动单帧识别和界面状态查询使用同一服务状态，避免线程并发下重复消费或互相覆盖。

### 5.2 稳定帧与高置信度

- 同一字段连续两次有效识别一致，且达到统一的高置信度阈值，才自动同步。
- 新局开始、采集源切换和画面场景变化后清空旧稳定帧缓存，避免跨场景沿用。
- 识别失败、`unknown`、缺失、越界或低置信度不代表空值，不得因此清空已有商店或阵容。
- 稳定缓存只保存最近候选，不写正式账本；同步后相同状态继续去重。
- 观测来源与置信度继续由现有 `provenance` 机制记录；人工纠错保持更高优先级。

### 5.3 绝对状态不重复执行动作

自动识别到回合、资金、等级和生命时，只通过观测处理器同步绝对值。不得调用 `refresh`、`level_up` 或 `next_round` 动作 reducer：

- 回合增加由现有回合观测维护时间线。
- 资金和等级以画面值为准，不再次扣款。
- 过回合收入不通过自动跟随重复结算。

### 5.4 商店与阵容

稳定且高置信度的商店直接由观测合并流程更新，不再需要“确认商店并计入本次刷新”作为正常流程的一部分。阵容同样使用现有合并规则；不完整识别只作为待确认信息，不覆盖已有有效数据。

## 6. 刷新事件归因

刷新统计与商店状态更新分离。只有同一同步链路同时满足以下证据时，才记录一次自动刷新：

- 同一场景、同一回合且调度中心等级未变化。
- 商店指纹发生有效变化，而非单槽位暂时识别失败。
- 资金变化与当前模式刷新费用一致。
- 没有可同时解释资金变化的阵容变化或其他待确认冲突。
- 相同批次或相同证据未被记录过，重试和重复帧保持幂等。

证据不足时不扣款、不重复生成商店、不猜测写入；界面显示“检测到可能的刷新，等待确认”。自动刷新通过专用的观测／统计入口记录，不复用带经济副作用的手工刷新动作。

## 7. 界面与交互

### 7.1 跟随状态

对局页显示“正在跟随／等待稳定画面／需要确认／已暂停／未连接”等明确文本，以及最近同步时间。状态不能只靠颜色表达；识别错误继续可见。

### 7.2 主操作与手动纠错

- 自动跟随正常时，主区域不再把“刷新／升级／过回合”作为必须点击的按钮。
- 三个动作与相关手工输入收进“手动纠错”折叠区，展开后仍可使用。
- 未连接、已暂停或手工模式时，手工操作直接可用。
- 高置信度商店同步后不再显示额外的“确认商店”步骤。
- 待确认项指出具体字段或事件，不要求玩家重复录入整局状态。

### 7.3 兼容已有界面

保留当前战术终端视觉系统、真实快照驱动和已有弹窗。此设计取代上一版界面规格中“刷新／升级／过回合始终形成主操作组”和“保留确认商店作为正常操作”的约定，其余布局与视觉约定不变。

## 8. 错误处理与数据安全

- 抓帧或识别异常时保留最后一次有效状态，并明确显示断开或失败原因。
- 任何单个字段失败不得使整帧服务崩溃。
- 重复帧、重复提交和服务重试不得重复记刷新。
- 自动同步与手工纠错共用引擎锁和存档机制，避免并发写入。
- 测试使用独立临时账本与演示帧；不清空、不改写用户已有存档。
- 保留 DeepSeek 的并发修改，修改前核对目标文件并备份，不覆盖无关文件。

## 9. 验证与验收

1. 单元测试覆盖相同帧去重、两帧稳定、低置信度拒绝、场景切换缓存失效及异常恢复。
2. 验证自动回合、资金、等级和商店同步不会触发重复扣款、重复收入或二次刷新。
3. 验证刷新仅在完整证据下记录一次；证据不足只提示，重复帧不重复计数。
4. 验证手工模式原有操作可用，账本重放及已有存档行为不回归。
5. 前端验证跟随状态、待确认提示、手动纠错和响应式布局。
6. 运行完整 Python、前端、自检和 HTTP 冒烟测试，并用演示采集源实际观察自动跟随。
7. 不将未在真实游戏画面上验证的识别准确率描述为已验证。

## 10. 完成标准

连接演示或游戏采集源后，可靠状态无需在插件重复操作即可跟随；正常自动模式下手工按钮不再是主流程，不确定变化不会被当作事实写入。用户能清楚看到插件是否正在跟随、何时同步，以及哪里需要人工纠正。

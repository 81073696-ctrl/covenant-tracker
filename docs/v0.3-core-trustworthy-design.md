# 卫戍协议·记牌器 v0.3 核心可信版设计

- 版本：v0.3.0
- 状态：设计已获用户批准，待文档复核后实施
- 实现目录：当前工作副本 `covenant-tracker-review`
- 原则：先保证规则、数据和分析可信，再扩展功能；所有未获官方确认的概率均标为估计

## 1. 背景与目标

当前版本已经具备本地对局记录、OCR 辅助、卡池推算和终局统计等基础能力，但部分规则与参考资料不一致，终局 JSONL 也无法还原每次刷新。v0.3 的目标是交付一个可用于真实对局的核心版本，而不是只修改版本号。

本轮目标：

1. 修正会改变记牌、购买和概率结论的核心规则。
2. 用独立事件账本记录对局过程，支持刷新分析和异常恢复。
3. 提供目标干员的刷新概率与实测记录，明确区分事实、模型和推测。
4. 收紧 OCR 状态合并与胜率统计口径。
5. 保留旧数据兼容性，并完成测试、自检和发布文档。

## 2. 非目标

以下项目不在 v0.3 核心可信版内：

- 置顶小窗与完整覆盖层。
- 装备系统。
- 多人同盟共享卡池的完整建模。
- 公开部署的社区统计服务。
- 将社区推测宣称为官方规则。
- 自动点击、自动购买或代替用户执行游戏操作。

## 3. 已考虑的实现方案

### 方案 A：独立对局事件账本（采用）

新增刷新、购买、出售、合成、升级和回合事件，旧终局记录继续导入。能够支持过程分析和恢复，改动适中。

### 方案 B：只扩展现有终局记录

实现较快，但无法还原刷新顺序和每次商店结果，无法支撑可信的 D 牌分析，因此不采用。

### 方案 C：整体移植参考项目规则引擎

可以复用部分逻辑，但迁移成本高，并会把参考项目中的推测一并带入当前程序，因此不采用。

## 4. 规则纠偏与证据等级

规则实现必须同时携带来源和置信度。UI 与文档不得省略“估计”标记。

| 规则 | v0.3 行为 | 证据处理 |
| --- | --- | --- |
| 休整期资金 | 默认在休整期结束清零；坎诺特等明确例外单独建模 | 参考实现与资料支持，保留来源 |
| 整备区已满 | 禁止购买，包括可能触发合成的购买；不放入临时区 | 核心规则纠偏 |
| 出售 | 普通和精锐均返还 1；精锐不再向上合成 | 核心规则纠偏 |
| 升级新增商店格 | 先保持为空，下一次刷新补货 | 核心规则纠偏 |
| 同店重复干员 | 允许不同格子出现同一干员 | 商店展示规则与概率抽样假设分开处理 |
| 回合收入 | 数据包采用 `min(3 + r, 12)` 的参考模型 | R1–R3 已验证；后续增长与上限仍需标记置信度 |
| 商店概率 | 按当前等级、剩余份数和商店格数估计；同店格子按参考模型独立估算 | 官方概率未公布，必须标为估计 |

规则变更应集中在规则与数据层，不在 GUI 中散落硬编码。测试必须覆盖例外和边界。

## 5. 对局事件账本

### 5.1 存储

每场对局拥有独立事件流，采用追加写入的 JSONL 文件。文件名包含 `match_id`，并带 schema 版本。终局摘要与过程事件分开保存。

每条事件至少包含：

```json
{
  "schema_version": 1,
  "match_id": "match-uuid",
  "seq": 42,
  "recorded_at": "ISO-8601 timestamp",
  "round": 5,
  "phase": "shop",
  "type": "refresh",
  "payload": {
    "shop_level": 4,
    "gold_before": 12,
    "gold_after": 10,
    "shop_after": [],
    "source": "manual"
  }
}
```

事件类型至少覆盖：

- `match_start`
- `refresh`
- `buy`
- `sell`
- `merge`
- `level_up`
- `round_end`
- `match_end`

`payload` 只保存该事件需要的字段。视觉识别和手工输入都通过相同的事件入口，避免两套状态逻辑。

### 5.2 一致性与恢复

- `match_id + seq` 作为事件身份，防止重复导入。
- 新事件通过 reducer 校验后追加；非法状态转换不写入账本。
- 写入失败时保留当前界面状态并给出错误，不假装保存成功。
- 启动时发现未结束对局，可按事件顺序恢复。
- 恢复与分析使用同一 reducer，避免界面状态和统计状态分叉。

### 5.3 旧数据兼容

- 保留旧终局 JSONL 的只读导入。
- 旧数据只参与其字段能够支持的终局统计。
- 不根据终局阵容反推或伪造历史刷新、购买和资金事件。
- 新统计查询应标明数据来自“过程事件”还是“终局摘要”。

## 6. D 牌记录与分析

### 6.1 刷新记录

每次刷新至少记录：回合、商店等级、刷新前后资金、刷新后的商店、目标干员（若已设置）、输入来源和识别置信度。

桌面端提供明确的刷新记录入口。OCR 结果足够可靠时可预填，用户确认后入账；无法可靠识别时允许手工输入，不猜测缺失数据。

### 6.2 模型估计

按目标干员、当前商店等级、已观测占池和商店格数计算：

- 单格出现概率估计。
- 一次刷新至少出现一张的概率估计。
- 达到指定把握所需刷新次数或资金估计。
- 当前已确认剩余份数及未识别占池的不确定范围。

在相同各格概率 `p`、格数 `n` 且采用独立抽样假设时：

`P(至少一张) = 1 - (1 - p)^n`

若各格概率不同，则使用对应各项乘积。公式旁必须显示模型假设；不得把估计值显示成官方概率。

### 6.3 实测分析

按对局和目标干员汇总：

- 刷新次数、出现次数与实际出现率。
- 平均及分位的命中刷新成本；样本不足时明确提示。
- 模型估计与实测结果并列，不相互覆盖。
- 可按模式、赛季和商店等级筛选。

### 6.4 统计解释

在场率、胜率、刷新行为分别统计。相关关系不得写成“多 D 必胜”等因果建议。统计界面显示样本量、筛选条件和纳入规则。

## 7. OCR 与状态合并

- 视觉观测按槽位合并，不因单帧空结果清空已确认单位或商店。
- 低置信度结果保留上一可信状态，并允许用户手工修正。
- 对同一槽位的变化要求明确证据；未知和空缺不能混为一谈。
- OCR 回合数增加时自动提交上一回合时间线。
- 事件载荷记录来源与置信度，使后续分析可排除低质量样本。

## 8. 终局统计口径

- 未完成第一回合便退出的 `quit` 记录不进入官方胜率口径。
- 已完成第一回合后的退出、正常胜负按既定规则纳入。
- 原始退出记录仍保留，可在原始记录查询中查看。
- 不同模式和赛季分别统计，避免混用规则与卡池。
- 所有比率同时显示分子、分母和样本量。

## 9. 桌面端交互

- 保留现有主界面和手工补录流程。
- 增加本局事件／刷新历史，可查看和纠正输入错误。
- 增加目标干员分析区域，展示剩余份数、估计概率、实测记录和样本提示。
- 纠正事件采用追加更正或明确的受限编辑策略，不能静默重写历史；具体实现以保持 reducer 可重放为准。
- 社区上传仍为可选能力，未配置服务时不影响本地功能。

## 10. 错误处理与隐私

- 本地账本写入、损坏和版本不兼容必须给出可理解的错误。
- 损坏事件文件不得被静默覆盖；保留原文件供恢复。
- 不上传过程账本，除非用户明确选择且上传接口支持相应数据。
- 旧社区统计接口继续校验记录长度、ID、结果、模式、赛季和阵容类型。

## 11. 测试与验收

至少覆盖：

1. 资金清零与例外、满整备区购买、出售返还、精锐合成边界、升级空格。
2. 特殊合成真实占池数与同店重复干员。
3. 事件顺序校验、重复事件、异常退出恢复、损坏文件保护。
4. 旧终局 JSONL 导入且不生成伪造刷新事件。
5. 单格与多格概率、空卡池、零概率、样本不足和估计标记。
6. OCR 空结果、低置信度、槽位合并和回合自动提交。
7. 第一回合前退出的统计排除及分子分母展示。
8. 全部现有测试和 `python -m covenant selftest` 继续通过。

发布验收：

- `covenant/version.py` 为 `0.3.0`。
- README 与实际功能一致，规则来源及置信度可查。
- 提供 v0.3 变更说明和已知限制。
- 所有新增测试通过，现有 45 项测试无回归。
- 不写入原项目目录，不自行提交 Git 历史。
